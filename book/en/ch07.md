# Software Is Never Done {#sec-ch07}

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
Sunday, March 1, 2026. Ten days earlier I had published on the blog what I called the "final post" about the weekly newsletter you watched being born in @sec-ch06. Lessons written down, conclusion done, a nice quote at the end. Done.

That Sunday, I opened my projects' history and did the math. Since that "done," the newsletter had taken another 56 commits. Adding the other three projects I had put live in February, it came to 125 [commits]{.gls key=commit} made after the day each of them was, in theory, finished.

The next day, Monday, subscribers would get the third issue. Generated, reviewed and sent by a system that hadn't stopped changing since it went live.

<!-- src: original -->
Meanwhile, the internet was still full of videos with a different promise. You write a good description of what you want, paste it into the chat, and the AI hands you back the finished system. A single request, the so-called [one-shot prompt]{.gls key=one-shot-prompt}: one request, no conversation, no going back.

Anyone on the outside who hears that asks the natural question. If I describe what I want properly, in a really well-written prompt, isn't that enough?

The four projects from that February answer it better than any opinion of mine. Every one of them drifted away from what was on paper a few hours after real people started using it.

## What the Paper Didn't Say

<!-- src: 2026/02/21/vibe-code-fiz-um-clone-do-mega-em-rails-em-1-dia-pro-meu-home-server -->
The case closest to the single-request dream was FrankMega. For a while I'd wanted my own service for sharing large files on my home server, a simplified clone of Mega, without depending on Google Drive or WeTransfer [@akita2026frankmega]. I wanted to know where the files are, how long they exist and who downloaded them.

One Saturday in February, I sat down and wrote a 56-line document describing what I wanted:

- upload one file at a time, with a link to share;
- a download limit per link and automatic expiration within 24 hours;
- login with password, a second factor and passkeys;
- no public sign-up, invite only;
- aggressive limits on attempts and automatic banning of anyone who abuses them.

At the end of the document I deliberately added one line: "suggest important features that may be relevant for a service like this." No spec covers everything, and I knew it.

<!-- src: 2026/02/21/vibe-code-fiz-um-clone-do-mega-em-rails-em-1-dia-pro-meu-home-server -->
I handed the document to Claude Code, with Claude Opus 4.6 behind it. The first commit came with 207 files and almost 7,000 lines of code. Full login, invites, an admin panel, drag-and-drop file upload, light and dark themes, 73 [automated tests]{.gls key=teste-automatizado}.

It's exactly what the ads promise. A document goes in, a system comes out.

Then I went to get it running on the server, and it broke: a piece of the system was missing when packaging the program to run on the server. After that, a browser security rule clashed with the way the program loads the page's scripts.

That was four fix commits in six minutes, just to get past "works on my machine."

### The 22 Flaws

<!-- src: 2026/02/21/vibe-code-fiz-um-clone-do-mega-em-rails-em-1-dia-pro-meu-home-server -->
The most important commit of the project came an hour later: a security audit that fixed 22 problems in the original code. Some were serious:

- the key that protects the login secrets had a default value written into the code itself, so anyone reading the source could decrypt every user's secrets;
- the second-factor code, the one that's valid for 30 seconds, could be reused several times within that window by whoever snooped it;
- after login, a malicious link could redirect the person to a third-party site;
- the download counter had a [race condition]{.gls key=condicao-de-corrida}.

That last one deserves an explanation, because it's the kind of bug no beginner imagines. The program read the number of downloads, added one and wrote it back. If two people click at the same instant, both read "4," both write "5," and a link that should allow only one more download allows two.

That bug doesn't show up when you test alone, with a single browser. It only shows up in production, when two requests arrive together.

<!-- src: 2026/02/21/vibe-code-fiz-um-clone-do-mega-em-rails-em-1-dia-pro-meu-home-server -->
Claude found and fixed all of it. But it found them because I asked, and I asked in a specific way. "Review security" is a vague instruction. "Check if there's a race condition on the download counter" is an instruction only someone who already knows that kind of bug exists can give.

Then came the saga of the download button: five commits in 21 minutes, trying to make the download work with the mechanism the framework uses to navigate between pages. Every attempt meant opening the real browser, clicking, seeing what happened, going back. The agent alone wouldn't have solved that, because the problem only showed up on screen.

<!-- src: 2026/02/21/vibe-code-fiz-um-clone-do-mega-em-rails-em-1-dia-pro-meu-home-server -->
And requirements popped up that the 56-line document never mentioned: a disk quota per user, so nobody fills up the server single-handedly; full translation into English and Portuguese; terms of service that must be accepted; decent error pages. Nobody predicts every feature on day one. You find out what you need by building.

By the end of that afternoon there were about twenty commits, roughly three hours of work and 210 tests. I put it live and wrote about it the same day.

### Three Days Later

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
Three days later, real users tried to share software installers: Mac files, Linux files, Windows files.

They couldn't. The program identifies the type of each file to decide what to accept, and those formats weren't on the initial list. Two commits, 22 lines, fifteen minutes of fixing.

Without those fifteen minutes, FrankMega was useless for the most common use case of a programmer's home server.

> No prompt in the world predicts that your users will want to share a Linux installer on day one.

## The Photo Detective

<!-- src: 2026/02/23/vibe-code-fiz-um-indexador-inteligente-de-imagens-com-ia-em-2-dias -->
The second project of that February was born from a problem lots of people have without being able to name it. I have a file server at home with terabytes of stuff piled up over decades. Somewhere in there is a payment receipt from 2019, saved as a photo named IMG_20190315_142301.jpg, in a folder with 3,000 more photos with similar names. I was never going to find it again.

The idea behind Frank Sherlock fit in one sentence: point the program at a folder, let an AI look at every image, describe what's in it and read any text that appears, and then search by content [@akita2026franksherlock]. "Receipt from such-and-such bank" instead of "IMG_2019 something."

I had one non-negotiable constraint: nothing could leave my machine. These are personal photos and financial documents. The AI model had to run here, on my GPU, without sending a single image to anybody's server.

### Measure Before You Build

<!-- src: 2026/02/23/vibe-code-fiz-um-indexador-inteligente-de-imagens-com-ia-em-2-dias -->
Before writing a single line of the app, I spent the night of Saturday, February 21, doing nothing but research. I set up a [benchmark]{.gls} (a standardized test, with known right answers, to compare models on the same ground; the subject gets a whole chapter in @sec-ch11). I set aside 94 files and recorded, for each one, the correct classification.

Intuition says a bigger model is a better model. The numbers said otherwise.

A small open vision model beat a competitor almost twice its size on every measure, and was a lot faster to boot. The giant version of the same model got practically the same right and took much longer, which, across hundreds of thousands of files, turns hours into weeks. And the newer models from the same family, released later, were worse at my task.

<!-- src: 2026/02/23/vibe-code-fiz-um-indexador-inteligente-de-imagens-com-ia-em-2-dias -->
I also did some back-of-the-napkin math on cost: running everything on my graphics card would come to tens of dollars in electricity, and sending it to a cloud company's API, thousands. The models, the timings and the math are in @sec-aptecnico-sherlock.

It was about two hours of tests that saved me days of rework from the wrong choice.

> Don't guess which model is best for your case. Measure.

### The Annoying Questions

<!-- src: 2026/02/23/vibe-code-fiz-um-indexador-inteligente-de-imagens-com-ia-em-2-dias -->
With the model picked, Sunday and Monday were heavy construction, with Claude Code writing most of the code. In the research and experiment phase, OpenAI's Codex seemed better to me; once I knew exactly what I wanted, Claude executed better. From Saturday night to Monday afternoon it was 50 commits and about 26 hours of actual work, with releases published for Linux, Mac and Windows.

The vision model made mistakes, of course. Any anime it didn't recognize, it guessed was *Evangelion*. But the descriptions, even imperfect, already made the search useful.

<!-- src: 2026/02/23/vibe-code-fiz-um-indexador-inteligente-de-imagens-com-ia-em-2-dias -->
What Claude didn't do was ask. None of the decisions that made the program reliable came from it; I had to ask for every one. They came from questions I asked almost by reflex, and from rules I imposed:

- what if the user cancels the scan halfway? It became a system of resume checkpoints, file by file;
- what if the database gets corrupted? It became automatic backups and a check on startup;
- what if the person doesn't have a good GPU? It became automatic selection of a smaller model;
- what if someone moves ten thousand photos to another folder? It became moved-file detection, without classifying everything again;
- the program never writes anything inside the scanned folders, because someone might point it at the company file server.

Think of an architect with an absurdly efficient construction crew. The crew works at night, doesn't complain, puts up walls in minutes. The architect doesn't need to lay bricks, but needs to know where each wall goes and what happens if you take one out. Without a blueprint, it's just a pile of bricks stacked quickly.

### From Index to Face Recognition

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
That first version was only the starting point. In the following days came another 53 commits. First, duplicate photo detection. Then videos, because real media folders have videos mixed in with photos and I hadn't thought of that.

And then came the feature I least expected to build. I started using the program with my real photos and caught myself thinking: "I want to find every photo of so-and-so." Frank Sherlock started detecting faces, grouping similar ones and letting you put a name to each person.

Before implementing it, I did the same thing I'd done with the vision model: a comparative test of the face detection alternatives, so I could choose with data. Then I implemented, and then I refactored. Measure, implement, clean up, the same cycle as always.

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
By early March, the project had 103 commits, and seventeen of them were just to get the program to build and publish properly on Linux, Mac and Windows, each system with its own quirks.

No model knows these things in advance for your project. That work takes someone who has been through that pain before.

My estimate is that an experienced programmer, without AI, would take at least three to four weeks to get to the same point. I took seven days. The speed is real, and the one who decided what to do with it was me.

## Life After Deploy

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
The newsletter, the one that was "done," is the best example of what happens after [deploy]{.gls key=deploy}, the moment the software leaves your machine and goes live. The 56 commits of the following ten days included thirteen bug fixes, and none of those bugs were in any spec.

A new section, about games, was born because the entertainment part only talked about anime and readers who play games were left out. The day it went live, the code that read release dates broke. The service the data came from returned dates with the months abbreviated in Portuguese, "fev," "mar," "abr," and the code expected the English format. That's the kind of thing you find out when it breaks.

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
The second issue came out longer than the first, and readers on Gmail didn't see the end. Gmail silently cuts off emails larger than about 100 kilobytes, and hides the rest behind a link few people click [@mxtoolbox2026clipping]. The fix was a size check before publishing and trimming some sections from ten items to five.

I tried switching the podcast's synthetic voice language from "Portuguese" to "auto." The voice model produced an accent that sounded like Lisbon Portuguese trying to pass for Rio. I reverted it the same day.

### M.Arvin and the Lukewarm Tone

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
M.Arvin, the newsletter's robot commentator you met in @sec-ch06, is written by an [LLM]{.gls}. Over time, he came down with a chronic ailment of these models: smoothing. Without intervention, every comment slides into the same lukewarm, polite, bland tone.

Worse, he opened almost every comment with "Ah,." You only notice it after reading thirty in a row and wanting to claw your eyes out.

It took seven prompt-tuning commits in ten days. I banned the formulaic patterns, killed the "Ah," opener, pulled M.Arvin out of entire podcast sections where he was contaminating the tone, and finally built a mood system: nine modes, from sarcastic to hopeful, that I pick for each story. Each of those tweaks only made sense after reading the previous output.

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
I also switched the system's default model, from Claude to Grok 4, because the previous model was weak in one particular area. The model name had lived in a single setting from the start, but it showed up repeated across 24 files. A whole commit just to make sure the next swap would be a one-liner.

Nobody does that cleanup on day one, because on day one you don't know you're going to switch models. It only happens when the pain shows up.

### The Circuit Breaker

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
The episode that best sums up that February was a small one. The newsletter queries a web search service to put together some sections, and that service started, every once in a while, answering "slow down, you're asking too much."

If I'd let the agent decide, it would have done what every tutorial teaches: try again, waiting a little longer each time. I asked for something else, a [circuit breaker]{.gls key=circuit-breaker}. If the service complains or takes too long, the program stops asking for two minutes and moves on with the section empty.

Why? Because I know newsletter generation runs at a fixed time and that, on the Sundays when the issue gets put together, search volume triples. A herd of repeated retries holding everything up is worse than one section with no results.

![Two reactions to the same error: keep retrying nonstop, or switch off for a while and move on.](assets/figures/en/ch07-disjuntor.png){#fig-ch07-disjuntor fig-alt="Two panels. On top, 'retry': a program sends repeated requests to a search service, which answers 'slow down, you're asking too much', while a queue of delayed requests grows beneath the program. Below, 'circuit breaker': a breaker trips and cuts the connection to the service, the program moves on with an empty section and the newsletter goes out, and a clock marks 2 minutes until the breaker resets."}

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
AI implements a circuit breaker in minutes, when you ask for it. It will never suggest one, because it doesn't know what time your system runs or what happens on Sunday. That knowledge comes from decades of running systems in production.

> The agent writes the code. I decide what code to write.

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
Even FrankMD, the editor from @sec-ch05, took on a life of its own in those weeks. Three outside people sent contributions, and I published version 0.2.0. One of them added an integration with the desktop environment's theme; I accepted it and, in the next commit, added more than 160 lines of fixes and tests, because I saw where it was going to break. Outside people show up to contribute when the project has passing tests, documentation and numbered releases.

### Why the One-Shot Prompt Is a Myth

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
Look at those 125 commits and tell me which one a spec could have predicted. The Gmail clipping, the months in Portuguese, the mixed accent, the repeated "Ah,," the Linux installer, the model spread across 24 files. Each was a decision made on the spot, with the system running, by someone who had context.

The one-shot fantasy is that a detailed enough spec produces the perfect software. But the perfect spec would require knowing in advance everything that's going to go wrong. And if you knew everything that's going to go wrong, you wouldn't even need the spec: the software would already be done in your head.

<!-- src: 2021/09/28/akitando-104-rant-empreendendo-com-software-do-jeito-errado -->
In 2021, well before agents, I was telling people who wanted to start a company with the whole software designed on paper: "Design emerges from the software, not the other way around" [@akitando104]. Software is never finished at version 1.0, and whoever thinks they wrote the last line probably built software nobody uses. AI gets to 1.0 faster, and what comes after it is still somebody's job.

> Good software comes out of hundreds of small decisions made with the system live, after contact with reality.

## Starting from Her Words

<!-- src: 2026/03/04/eu-fiz-um-sistema-de-data-mining-pra-minha-namorada-influencer-dicas-e-truques -->
Around the same turn from February to March, I did a project for a user who wasn't me. My girlfriend is a geek culture influencer. She does interviews, covers conventions, produces content for several platforms and negotiates with sponsors, in a professional operation she runs herself with a lean team.

And that whole operation depended on grunt work: open each social network, jot down numbers, compare with competitors, check the events calendar, read comment after comment. The system I built for her is private, so I'll tell you about the process and the lessons, without the details.

<!-- src: 2026/03/04/eu-fiz-um-sistema-de-data-mining-pra-minha-namorada-influencer-dicas-e-truques -->
Before thinking about any architecture, I asked her to talk freely about what she wanted. No technical jargon, no form. I wrote her words down in a document, and a few sentences became the project's north star:

> *"My biggest difficulty today is figuring out what kind of content to make that can really take off and why the ones that worked actually worked."*
>
> *"How much I should/could charge for a sponsored post, based on engagement research, competition, sponsors, events."*

She didn't ask for a dashboard full of charts or a PDF report. She asked for answers to concrete day-to-day problems. If I had started from the technical spec, I'd have spent weeks designing a dashboard she would never open.

<!-- src: 2026/03/04/eu-fiz-um-sistema-de-data-mining-pra-minha-namorada-influencer-dicas-e-truques -->
What came out was a system with no screen at all. It collects data overnight, cross-references it with a calendar of conventions and releases, and talks to her on Discord, where she already spends her day. She asks in Portuguese "how did my posts do this week?" and an assistant answers with real numbers.

Behind the scenes, the assistant uses [tool calling]{.gls key=tool-calling}, the mechanism from @sec-ch03 where the model asks the program to run a tool and reads the result. There are more than forty tools, each one a database query. The model picks which ones to call, gets the data and writes the answer.

<!-- src: 2026/03/04/eu-fiz-um-sistema-de-data-mining-pra-minha-namorada-influencer-dicas-e-truques -->
Along the way, the plan changed. The original idea was a weekly email report. I swapped it for five daily digests right there on Discord, one topic per weekday, each item with buttons for her to mark what was useful. That change, which wasn't in any plan, was probably the one that improved her life the most.

It took three days and 58 commits, with Claude writing a good chunk of the code. It didn't know what a Brazilian influencer needs. Neither did I, but she told me.

## Zero and Nothing

<!-- src: 2026/03/04/eu-fiz-um-sistema-de-data-mining-pra-minha-namorada-influencer-dicas-e-truques -->
When the system started running on real data, a bug showed up that I consider one of the most instructive of the whole year.

One of the social networks doesn't report how many times each post was shared. The data simply doesn't exist at the source. In the database, that field stayed empty. And the model, analyzing the numbers, read the empty as zero and concluded, with all the confidence in the world, that nobody shared her posts on that network.

To a programmer, empty and zero are different things. Empty means "I don't know." Zero means "I measured, and it came out zero." The model cheerfully mixes the two unless you explicitly tell it not to.

![An empty field and a measured zero look the same to the model, unless someone spells out the difference.](assets/figures/en/ch07-zero-e-nada.png){#fig-ch07-zero-e-nada fig-alt="Two cards side by side. The one on the left has the shares field empty, with a question mark, the label data not available and the note 'the source doesn't report this number'. The one on the right shows the number zero with a check mark and the label measured. A dashed arrow, marked 'read as zero', runs from the empty card to a chatbot's speech bubble with the wrong conclusion, crossed out: 'nobody shares your posts'."}

<!-- src: 2026/03/04/eu-fiz-um-sistema-de-data-mining-pra-minha-namorada-influencer-dicas-e-truques -->
The fix was a reusable snippet of instructions, included in every prompt that handles numbers. When a field is empty, say "data not available for this platform" instead of "zero." When a field is zero, report it normally, because the data is real.

The second bug was with dates. I asked the assistant for a reminder for "tomorrow at 3pm," and it set the reminder on a date in 2024. The model has no clock; it doesn't know what day it is (why it makes things up with such conviction is the subject of @sec-ch04, where we talk about [hallucination]{.gls key=alucinacao}). The fix was to inject the current date and time into every prompt that deals with time and tell it to calculate from there.

<!-- src: 2026/03/04/eu-fiz-um-sistema-de-data-mining-pra-minha-namorada-influencer-dicas-e-truques -->
The third surprised me by how often it happened. The model gets tool parameters wrong more than you'd think: it asks for a hundred results where the max is fifty, it sends a username in the wrong format. Every one of those errors triggers a correction round trip, which costs time and money. The way out was to make each tool fix up whatever comes in on its own: an out-of-range value becomes the nearest limit, a name gets cleaned up.

And the fourth bug was mine. Two different prompts gave contradictory instructions on how to handle the empty values, one said to use zero and the other said to use empty. The model obeyed one or the other depending on the day. Centralizing those rules in single snippets, reused by every prompt, killed off the whole class of inconsistency.

### Defensive Engineering

<!-- src: 2026/03/04/eu-fiz-um-sistema-de-data-mining-pra-minha-namorada-influencer-dicas-e-truques -->
The outside world doesn't cooperate either. One of the networks blocks data collection at random, roughly once every five attempts, no matter how careful the program is. I swapped the main source for a paid service and kept my own collection as the fallback.

That's why every automated task in the system was written so it can run twice in a row without duplicating anything and without breaking anything. That has a name, [idempotency]{.gls key=idempotencia}. If a collection run dies halfway and starts over, the result is the same as a run that went through only once.

<!-- src: original -->
Notice the pattern in the first three bugs. No line of code was written wrong; the LLM did exactly what an LLM does: filling the gap with the most likely thing, guessing a plausible date, picking a round number for a parameter.

Anyone who puts an LLM inside a system has to treat its output the way they'd treat input from an unknown user. Check it, limit it, normalize it, flag when data is missing. The whole system has to be designed expecting the model to get things wrong, because it will.

> A system with AI inside has to defend itself from its own AI.

<!-- src: original -->
That goes for you too, even if you never write a line of code. When an assistant tells you a number is zero, ask whether it measured it or just didn't find it. When it gives you a date, check the calendar.

## Competence in the Mirror

<!-- src: 2026/02/21/vibe-code-fiz-um-clone-do-mega-em-rails-em-1-dia-pro-meu-home-server -->
Back to FrankMega's 56-line document. It looks simple, a wish list. But every line carries years of experience.

I asked for attempt limits because I've seen services taken down by bots. I asked for automatic banning because I've dealt with abuse. I asked for an atomic download counter because I understand what happens when two things arrive at the same time.

If a beginner wrote the same document, they probably wouldn't have half of those concerns. And the model wouldn't spontaneously suggest any of them. The result would be a service that's functional, pretty, and completely insecure, delivered by the same AI, at the same speed.

It's the mirror from the end of @sec-ch06, seen up close, line by line:

> AI is the mirror of your own competence.

<!-- src: 2026/03/01/software-nunca-esta-pronto-4-projetos-a-vida-pos-deploy-e-por-que-one-shot-prompt-e-mito -->
The mirror works the other way too. There are experienced programmers who saw the AI mess up three times, declared "this is useless" and went back to doing everything by hand. I get it. It hallucinates, generates subtle bugs, overcomplicates what was simple, and I documented every one of those defects.

But the question for that colleague is: have you never made the very same mistake? Never spent two hours reading documentation only to find out it was a typo in the config? When the AI gets it wrong in a project with good tests, checked by someone who understands, the error shows up early and the fix takes minutes. Without that checking, the tests the model itself wrote can certify the error instead of catching it, as @sec-ch12 shows.

Using AI here and there, like glorified autocomplete, also leaves about 90% of the gain on the table. What I did that February was full-time pair programming with an agent, from the first commit to production, with the same discipline I'd have with a human pair. That came to four public projects in production in one month (not counting the private system from the previous section), 692 commits and more than 4,000 tests.

The discipline is [XP]{.gls key=xp}'s, which we saw in @sec-ch06: [TDD]{.gls key=tdd}, small releases, green [CI]{.gls key=ci}, continuous refactoring. AI is the accelerator. Those practices are the brake and the steering wheel. Without them, AI produces fast code that piles up debt even faster.

To anyone still waiting for AI to "get better" before really using it, my answer from that March still stands: it's already good enough. The bottleneck is learning to work with it.

And to anyone who got this far hoping for the single request that solves everything, the answer is the one in the title. Finished software is dead software. As long as somebody uses it, it changes, and somebody has to decide how.

Except a mirror shows whatever is in front of it, including when what's in front of it is you getting it wrong. In those same weeks, I was buried in another project, a manga reader that needed to find the speech balloons on every page. The agent wrote filter after filter, every fix broke something else, and the program kept mistaking faces for balloons.

For the first time in the marathon, all that speed only served to produce, faster and faster, code that didn't solve the problem.
