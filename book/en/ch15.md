# An Intern with Root Access {#sec-ch15}

<!-- src: ref:private-notes/nas-postmortem.md -->
On Saturday, October 10, 2026, I asked for a cleanup. The downloads folder on the old NAS, the network storage box where I keep everything, was crammed. Most of it had already been copied into the movie, TV and music library. The rest was either still downloading or had never been imported.

<!-- src: 2026/10/06/desastre-no-meu-nas-como-quase-perdi-90-tb-de-dados -->
That NAS was sick. Since Monday, October 5, five days earlier, I had been pulling the data off it in a hurry, in a week in which I nearly lost every file I own. That story comes after the cleanup, in @sec-ch15-nas.

<!-- src: ref:private-notes/nas-postmortem.md -->
The request was simple: delete what's already in the library and keep the rest.

The one who ran it was the [agent]{.gls key=agente} that manages my home server. It built a keep-list, everything that must not be deleted, by asking the download program, which knows what's still in progress. Except that program had stopped on its own in the small hours of that night, for a reason nobody ever found, and the agent didn't notice.

A program that has stopped doesn't answer. The query came back empty, and an empty keep-list protects nothing.

<!-- src: ref:private-notes/nas-postmortem.md -->
The agent ran the deletion anyway. In the report it wrote afterwards, it boiled the cause down to one sentence: the program was stopped, the query returned nothing, "and I didn't check the list."

Sixty-nine items were deleted. The audit, done item by item once the scare was over, showed the size of the damage:

- 58 of them had a copy in the library, so nothing was lost there;
- 11 were music albums that had never been imported and had no copy anywhere.

The 31 incomplete downloads, the whole reason the keep-list existed, were untouched, by luck.

<!-- src: ref:private-notes/bulk-delete-runbook.md -->
They came back. The old NAS had taken an automatic [snapshot]{.gls key=snapshot} at midnight, a photograph of the folders' state that lets you return to exactly that moment. That snapshot, from hours before the cleanup, still had all eleven. They were copied back. (That copy almost slipped through with a half-written file, as I tell right after this.)

What happened next interests me more than the mistake.

## Who Checked the Plan

<!-- src: ref:private-notes/nas-postmortem.md -->
The cleanup wasn't finished. About 785 entries were left that had been classified as safe to delete, more than 2 TB. This time each one was checked against the import history of the programs that organize the library, and against the file actually existing in the library. Another 186 were put on hold for me to decide one by one.

The server agent wrote the procedure, but a different one ran it: the agent on my desktop, which has direct access to both NASes. The two talk through a message system I wrote myself (it shows up in @sec-ch20). One leaves its report in the other's inbox, and I follow the conversation.

<!-- src: ref:private-notes/bulk-delete-runbook.md -->
While running it, the second agent found two defects in the procedure.

The first was an overzealous safety check. To stop a malicious file name from making the command climb out of its folder and delete things elsewhere, the procedure refused any name containing two dots in a row. Album names have ellipses, though, and a record called "Oops!... I Did It Again" would have been rejected as a threat.

The second defect was worse. When restoring the eleven albums, the procedure treated "the file exists" as a synonym for "the file was restored." The agent got suspicious, went and measured, and found a real case: a copy interrupted halfway had left a half-written file behind. It existed, and it was incomplete.

<!-- src: ref:private-notes/nas-postmortem.md -->
In the end, the 785 entries were deleted without a single failure and the eleven albums were restored at the exact size of the original. Both were verified independently. The two defects were fixed and became a written procedure for next time.

New rules came with them, mandatory for any agent that touches my data:

- every keep-list must be checked before anything runs: it can't be empty, and it must hold the expected number of items;
- every assumption of the "this was already copied" kind must be verified item by item before a destructive operation;
- "the file exists" never again counts as proof that the file is whole.

<!-- src: original -->
Hence the title of this chapter. Root is the name of the administrator account on a Unix system, the one that can do anything, including deleting the system itself. An AI agent working on your computer looks a lot like a hard-working intern someone handed that password to. It's fast, eager to help, follows instructions to the letter and, every now and then, trusts an empty list.

The question you may be carrying is whether a thing like this can wreck your computer or make your files disappear. It can. The question I spent the year answering is a different one: what has to be in place so that, when it happens, it costs nothing.

## Ninety Terabytes Hanging by a Thread {#sec-ch15-nas}

<!-- src: 2026/10/06/desastre-no-meu-nas-como-quase-perdi-90-tb-de-dados -->
To understand why I was cleaning up a sick NAS, go back five days before the cleanup. On Monday, October 5, 2026, I was woken up at 8 a.m. by a loud, insistent beep. I knew it was the NAS before I opened my eyes.

Two drives marked as critical, in an array that could only survive losing one.

My NAS had eight drives arranged in what technicians call single-parity RAID. Files don't sit whole on a single drive: each file is chopped into blocks spread across all the drives, along with an extra piece of information, the parity, which lets the system recompute the chunk from a drive that died. With one drive lost, the math works out. With two, it doesn't anymore.

<!-- src: 2026/10/06/desastre-no-meu-nas-como-quase-perdi-90-tb-de-dados -->
Hard drives die, sooner or later. Backblaze, which runs hundreds of thousands of drives and publishes the statistics, measured an annualized failure rate of 1.7% in the second quarter of 2026, and 1.4% a year over the whole fleet's lifetime [@backblaze2026q2]. That sounds small until you run the numbers for eight drives at the lifetime rate: about an 11% chance that at least one fails within a year, and more than 40% within five.

Which is what happened. I had swapped an old drive for a bigger one, a routine upgrade. To rebuild onto the new drive, the array has to read every other drive end to end, more than 100 TB of continuous reading. One of the old drives had bad sectors hiding in a corner nobody had read in a long time, and it gave out in the middle of the process.

<!-- src: 2026/10/06/desastre-no-meu-nas-como-quase-perdi-90-tb-de-dados -->
According to the logs, the vendor's software had known that drive was failing for more than a month. I had email notifications set up, and they worked: when the disaster blew up, I got a flood of alerts. Before that, not one.

Luckily, the files were still readable. I bought a second NAS in a hurry, paying more than three times what it would cost in the US, import and rush included, because someone shopping on a Monday morning with a dying drive is in no position to haggle. And I started copying about 90 TB from one to the other.

### Who Ran the Recovery

<!-- src: 2026/10/06/desastre-no-meu-nas-como-quase-perdi-90-tb-de-dados -->
Almost none of the recovery was me typing commands. It was run by the same two agents from the cleanup: the desktop one handled both NASes, and the home server one handled the 57 services that depended on the storage.

I made the decisions. They executed, measured and, a few times, screwed up badly.

The first stumble belonged to the new NAS's copy program, and an agent caught it. The program reported success, all green. When the agent compared what existed at the source with what had arrived at the destination, two holes appeared:

- a 901 GB folder belonged to another user on the system, the program had no permission to go in, and it simply skipped it without telling anyone;
- 113 files with names the program considered "unsupported" were left behind, recorded on a detail screen nobody opens during a copy that takes days.

> A backup tool that reports success while omitting what it couldn't read is worse than one that fails screaming. Verify the backup against an independent inventory of the source, never against the tool's own log.

<!-- src: 2026/10/06/desastre-no-meu-nas-como-quase-perdi-90-tb-de-dados -->
The agents also made mistakes of their own. At one point, one of them relaunched the copies "from scratch" and checked whether the old processes had died. The tool that lists processes on that NAS truncates the command line, the search found nothing, and the agent concluded everything was clean.

It wasn't. There were 32 copies running at once, fighting over the same sick drive, with the cable carrying more than three times what the drive could read and the new NAS choking on everything it was receiving. The fix was to stop trusting that tool and count the processes straight at the source. Once I killed the extra processes, the useful copying got faster.

<!-- src: 2026/10/06/desastre-no-meu-nas-como-quase-perdi-90-tb-de-dados -->
The subtlest stumble was in the verification. Every finished copy went through a check, and the check inherited the copy's exclusion filters. A folder excluded from the transfer was excluded from the proof as well.

Rerunning the check without filters turned up 952 files and 191 GB missing, precisely some batches I had set aside as the only existing copy. A verification that uses the same filters as the copy only confirms the copy's assumptions.

In the end, there were 17 copy jobs, all verified, about 5.9 million byte-identical files. The old NAS was only shut down after every folder had been proven on the other side. I lost nothing by accident.

![The right question compares the destination with the source; the tool's report only repeats what it thinks it did.](assets/figures/en/ch15-verificar-na-origem.png){#fig-ch15-verificar-na-origem fig-alt="Two verification paths side by side. On the left, a backup tool looks at its own report and shows a green light, while a folder was left out without warning. On the right, an independent list of the source files is compared item by item with the destination, and the missing folder shows up flagged in red."}

<!-- src: original -->
Notice the pattern. The copy program believed it had copied everything, the agent believed it had killed the processes, the verification believed the filters. And, that same Saturday, the cleanup agent believed an empty list.

In every case, someone trusted their own account of the work instead of going to check the thing itself. And in every case, what saved the day was a measurement taken straight at the source: counting the source's files, counting the actual processes, measuring the size of the restored album. It's the same principle as the [oracle]{.gls key=oraculo} in @sec-ch08, the check that doesn't depend on whoever did the work saying they did it.

## Why the Agent Holds the Keys

<!-- src: 2026/03/01/ai-jail-sandbox-para-agentes-de-ia-de-shell-script-a-ferramenta-real -->
A reasonable question at this point is why anyone gives that kind of access to a program that makes mistakes. The answer is that, without access, the agent is good for almost nothing.

A coding agent (the kind you met in @sec-ch03) needs to read the project's files, run the compiler, the tests, the search tools, the most mundane system commands. Each of those commands runs with your permissions. If it can delete one file in the project, in principle it can delete any other file you could.

<!-- src: 2026/07/11/como-me-precaver-pros-meus-agentes-nao-apagarem-minhas-coisas -->
The tools know this and, by default, ask for permission before every command. In practice, after the fiftieth "may I list the files?," everyone gets tired and picks the option that unlocks everything for the rest of the session.

The jargon for this is [YOLO mode]{.gls key=modo-yolo}, from *you only live once*. In Claude Code, the option that turns it on is called, without a shred of subtlety, "dangerously skip permissions." The agent runs whatever it wants, whenever it wants, without asking anything.

<!-- src: 2026/03/01/ai-jail-sandbox-para-agentes-de-ia-de-shell-script-a-ferramenta-real -->
There's a second risk, and it doesn't depend on the model making a mistake. Software projects use third-party libraries, downloaded by the thousands from public repositories. Every so often one of those libraries gets compromised and starts carrying malicious code, which is called a [supply-chain attack]{.gls key=ataque-cadeia-de-suprimentos}.

If the agent installs one of those libraries, the malicious program runs with the agent's permissions, which are yours. The model's good intentions guarantee nothing, and this kind of attack doesn't pick its victims.

### The July Headlines

<!-- src: 2026/07/11/como-me-precaver-pros-meus-agentes-nao-apagarem-minhas-coisas -->
Remember the news that closed the previous interlude? In July 2026, the talk online was LLMs deleting other people's files. Matt Shumer posted that GPT-5.6 Sol had deleted almost all the files on his Mac: a second agent, assigned to review the first one's work, built the path to his home folder wrong and ordered everything in it deleted [@shumer2026deleted]. The next day, another user reproduced the behavior on a disposable environment, and a sync command swept away system folders to the point of needing a full reinstall [@goodalexander2026devnet].

The discussion degenerated into the same two extremes as always: on one side, "see? AI is dangerous, never let it run anything on its own"; on the other, "whoever lets an agent loose deserves what they get." I found both sides lazy.

<!-- src: 2026/07/11/como-me-precaver-pros-meus-agentes-nao-apagarem-minhas-coisas -->
That July I had been using agents almost all day for five months, the last two entirely in YOLO mode. Almost 40 new repositories, more than 500 thousand lines of code, and no file deleted without my asking.

My frustrations with them were of a different nature: stubbornness, lazy solutions, context getting lost. Annoying things, but miles away from wiping my home folder.

My hypothesis, then, was that many of these accidents came from vague requests: "clean this up" without defining what counts as trash, "fix it" without giving context. The agent executes the instruction you wrote, with all the ambiguities you left in it.

<!-- src: original -->
Three months later, the cleanup at the start of this chapter handed me a case that doesn't fit that hypothesis. The request was clear, and the rule for what to keep was explicit. The failure was in an assumption nobody checked: that the keep-list had anything in it. The conclusion I drew in July came out stronger.

<!-- src: 2026/07/11/como-me-precaver-pros-meus-agentes-nao-apagarem-minhas-coisas -->
I don't trust LLMs completely, and nobody should. The difference is what you do with that distrust. You can turn it into panic, into an outraged post or into a ban. I prefer to turn it into engineering.

> The right question is why a single wrong command, from any origin, has the power to cause unrecoverable loss on your machine.

## The Jail

<!-- src: 2026/03/01/ai-jail-sandbox-para-agentes-de-ia-de-shell-script-a-ferramenta-real -->
The first layer is not letting the agent see what it doesn't need. The technical name is [sandbox]{.gls}: an isolated environment where a program can only see and change what you allowed. The kid plays all they want inside the box, and the sand doesn't spill into the rest of the yard.

In January 2026 I built mine with a script of about 170 lines, using bubblewrap, the same piece that isolates apps installed through Flatpak on Linux. Two months of daily use showed the script's limits, and in March it became a real tool, which I named ai-jail [@akita2026aijail; @aijail2026site].

<!-- src: 2026/03/01/ai-jail-sandbox-para-agentes-de-ia-de-shell-script-a-ferramenta-real -->
The idea is simple to describe. When the agent runs inside the jail, it sees a computer that looks normal, but only the current project's folder is real and persistent. The rest of your home folder shows up empty, in a temporary area that evaporates when the session ends.

The most sensitive folders, such as the keys that give access to your servers, cloud service credentials and browser profiles with saved passwords, never even go in. The agent can't even see that they exist.

If it decides to delete everything in your home folder in there, it deletes a scratch copy that was going to vanish anyway. Your real home folder was never even mounted.

<!-- src: 2026/03/01/ai-jail-sandbox-para-agentes-de-ia-de-shell-script-a-ferramenta-real -->
The jail pairs with a safety net every programmer already has: Git, the system that keeps the history of every [commit]{.gls} in the project. If the code lives in a remote repository and the agent can't push anything there without my approval, the worst it can do is wreck the local copy. Then I go back to the last commit, or delete the folder and clone it again. The remote was never touched.

### What the Jail Promises, in Its Own Words

<!-- src: ref:ai-jail/docs/SECURITY.md -->
Over the year ai-jail grew a lot, and the documentation became clearer about what it promises. The first sentence of the security document asks you to read this before anything else: it is "an accident guard," with no pretension of being a security boundary. It exists to contain the mistakes of an agent you trust but that is fallible; against an attacker determined to break out, it promises nothing.

For truly hostile code, the documentation itself tells you to use a disposable [virtual machine]{.gls key=maquina-virtual}, an entire simulated computer you throw away afterwards.

<!-- src: ref:ai-jail/README.md -->
That candor shows in the defaults. The jail deliberately exposes the credentials of the very agent you're running, so it starts out logged in instead of asking you to log in every session. The document states flat out that this is a trade-off: anything running inside can use those credentials for as long as the session lasts. If you don't accept the trade, you turn on an option and run isolated, logged out.

The network follows the same logic: it comes closed, with a filtered passage only for what the agent needs to work, such as the model's server. Everything else stays blocked.

<!-- src: ref:ai-jail/README.md -->
For those who want the maximum, there's a full lockdown mode: project read-only, network cut, almost everything turned off. Even that mode, the documentation warns, is still not a virtual machine. (The step-by-step for setting up your own jail, with ai-jail or another tool, is in @sec-apB.)

### The Back Door

<!-- src: 2026/07/25/ai-jail-update-seguranca-docker-opt-in -->
On July 25, 2026, a user opened a report on the ai-jail repository with a title no sandbox author ever wants to read: sandbox escape via Docker, with root access on the host computer [@mdindoffer2026docker].

Docker is the most widely used tool for running [containers]{.gls key=conteiner}, small isolated environments where a program runs along with its dependencies. Coding agents use it a lot, to spin up a test database, for instance. For convenience, ai-jail let the agent talk to Docker from inside the jail, by default.

<!-- src: 2026/07/25/ai-jail-update-seguranca-docker-opt-in -->
The problem is that the thing answering Docker's requests is a program that runs as root, outside the jail. An agent in there could politely ask Docker to create a container with the computer's entire disk mounted inside, and read any file as administrator. Docker's own documentation warns that only trusted users should have that access [@docker2026security].

None of the jail's walls could see this. The agent didn't even need to escape: the jail had a door straight into the engine room.

<!-- src: 2026/07/25/ai-jail-update-seguranca-docker-opt-in -->
I knew, in the abstract, that this was dangerous; I had even written it in the documentation. What I hadn't internalized is that a danger like that, switched on by default, is already a vulnerability. The fix shipped the same day: Docker access now comes switched off and only goes in if you ask for it explicitly, and when you do, the jail warns you at launch that this amounts to giving the agent root.

I publicly thanked the person who reported it. It came with a precise description, a repro in a few lines and a proposed fix, which is how you report a flaw in an open project.

> A sandbox with a back door left open for convenience loses a good part of its value. A security layer you don't audit turns into decoration.

### Two Audits, the Same Two Holes

<!-- src: ref:ai-jail/docs/SECURITY_AUDIT_2026-09-30_COMPARISON.md -->
On September 30, 2026, the ai-jail code went through two security audits on the same day, of the same version. The second was done without reading the first, and only after it had closed its own list were the two compared.

Each on its own, both found the same two high-severity problems, and both problems were reproduced in practice. In plain language:

- a malicious project could forge some Git configuration files and talk the jail into opening, with write permission, any folder on the computer outside the project;
- a trick with a duplicated entry in the environment variables (the settings programs read at startup, where passwords often live) let a real password into the jail, in a spot where only a fake placeholder was supposed to go.

<!-- src: ref:ai-jail/releases/v2.4.0.md -->
Both holes were closed in the next version, tagged that same night. But I learned the most from what each audit let slip.

<!-- src: ref:ai-jail/docs/SECURITY_AUDIT_2026-09-30_COMPARISON.md -->
Beyond the shared findings, the first one found more than ten problems the second didn't see, including everything that only shows up on a Mac. The second found three the first one missed, among them a testing shortcut left inside the published program. And it dismissed or left in doubt three problems that, once the analysis was redone, were real.

The comparison document itself concludes that neither one, alone, was complete. The list to fix was the union of the two.

<!-- src: original -->
It's the same lesson as the double review in @sec-ch06, where each agent caught something different and none of them caught everything. And it's the same lesson as the cleanup: the agent that wrote the procedure didn't see the defects, while the one that read it with the eyes of someone about to run it did. An independent second pair of eyes catches what the first misses, whether those eyes belong to a person or a machine.

## Layers

<!-- src: 2026/07/11/como-me-precaver-pros-meus-agentes-nao-apagarem-minhas-coisas -->
The jail is the layer closest to the agent, but it only covers the session. The eleven albums from the start of the chapter were deleted by an agent running outside any jail, with legitimate access to the folder, doing exactly the kind of work I had given it access for. What saved them was the next layer.

### The Undo Button

<!-- src: 2026/07/11/como-me-precaver-pros-meus-agentes-nao-apagarem-minhas-coisas -->
I've been arguing for years that everyone should use a file system with snapshots, long before coding agents existed to take the blame. I recorded an entire episode of my channel about it in 2023 [@akita2023akitando146]. The argument was the same as today: your data needs to survive human error. An LLM deleting the wrong folder is just a new category of human error, outsourced.

The trick that makes snapshots cheap is called [copy-on-write]{.gls key=copy-on-write}. This kind of file system never overwrites data in place: it writes the new version somewhere else on the disk and only updates the index. A snapshot freezes the index as of that moment, without copying anything.

It's instantaneous and nearly free. Only what changes from then on starts taking up extra space.

<!-- src: 2026/07/11/como-me-precaver-pros-meus-agentes-nao-apagarem-minhas-coisas -->
In July, my machine kept 23 system snapshots, and the cost was the difference between them, a few gigabytes. You browse a snapshot like a regular folder: the agent deleted your project at 3 p.m., the 2 p.m. snapshot still has everything. Recovery takes seconds.

On Linux, this comes from file systems like Btrfs. On the Mac, the default file system does the same, and Time Machine takes local snapshots automatically. On Windows the story is weaker, and anyone developing there should treat external backup as mandatory.

<!-- src: 2026/10/06/desastre-no-meu-nas-como-quase-perdi-90-tb-de-dados -->
The same goes for the whole system. During the NAS recovery, an update to the core of my home server's operating system started knocking its drive offline at night, silently. That machine's system updates in blocks and keeps the previous version as a snapshot, so going back to the previous version took one reboot. Without system snapshots, that night would have cost a reinstall.

### The Copy That Lives Somewhere Else

<!-- src: 2026/07/11/como-me-precaver-pros-meus-agentes-nao-apagarem-minhas-coisas -->
Snapshots have an obvious limit: they live on the same drive as the data. If the drive dies, both die together. That's why the second thing I've been repeating for years is that everybody needs an external [backup]{.gls}, on a separate hard drive, a NAS or the cloud.

On my desktop, a backup program runs every night at 3 a.m. and stores an encrypted copy on the NAS. It keeps seven daily copies, four weekly, six monthly and one yearly. None of it requires me to remember anything.

The two layers complement each other. The snapshot fixes the accident from minutes ago, in seconds. The backup fixes the disaster from days ago, dead drive included. An agent would have to be very dedicated to punch through both, and even then there would still be last night's copy, on a device it can't even reach.

<!-- src: 2026/10/06/desastre-no-meu-nas-como-quase-perdi-90-tb-de-dados -->
The NAS taught me that this layer has layers too. Parity protects against one dead drive inside the box; against losing the whole box, only another copy somewhere else will do. I know that, I teach that, and I still only had an off-site copy of part of the collection. I came out of that week with two NASes, each surviving the loss of two drives, scheduled snapshots, a daily backup and a cloud copy of what's critical.

### Agents Stay Out of Production

<!-- src: 2026/07/11/como-me-precaver-pros-meus-agentes-nao-apagarem-minhas-coisas -->
Everything so far is about my computer and my home. At a company, the bar goes up, and rule number one is simple: no AI agent should have access to [production]{.gls key=producao}, the real system that serves customers. No direct access to the servers, no database password, no admin key.

If your agent can delete the customer database, the problem stopped being the AI a long time ago. Any intern with the same access is the same time bomb, just typing slower.

<!-- src: 2026/07/11/como-me-precaver-pros-meus-agentes-nao-apagarem-minhas-coisas -->
I do advocate agents in a test environment, though. Even there, there's a right way. Instead of asking for one-off actions ("install that over there," "restart that service," "run this command on the database"), the agent writes recipes: files that describe the desired configuration, kept in version history, that can be read, reviewed and run again as many times as needed.

The agent does the heavy lifting. It writes the recipe, applies it to the test environment, runs the tests, watches the result and adjusts until it's right. Then a human reviews it and promotes it to production, following every step. The finger that presses the production button has a name on a payroll.

<!-- src: 2026/07/11/como-me-precaver-pros-meus-agentes-nao-apagarem-minhas-coisas -->
And production, by definition, requires two things many companies pretend to have. Real backups, tested, with rehearsed restores. And monitoring: if you can't see the state of the system, what you have is a server plugged into an outlet and a prayer.

> Never run anything in production that you can't recover from.

## What This Has to Do with You

<!-- src: original -->
Maybe you'll never run a coding agent. That doesn't leave you out. You already let software act on your files all the time: the app that syncs a folder with the cloud, the "cleaner" that promises to free up space on your phone, the assistant that organizes your photos, and now the AI assistants that read and touch your computer and your email.

All of them can fail the same way my agent did. A sync that reads an empty folder as the new state of things and deletes the cloud copy makes the same kind of mistake as a cleaner that calls "junk" what you wanted to keep.

<!-- src: original -->
The layers in this chapter, translated for people who don't program, fit into a few habits:

- before letting any program delete, move or "organize" in bulk, have a copy somewhere else;
- find out whether your computer or your cloud service keeps old versions of your files, and for how long, before you need it;
- keep a backup that physically lives away from the original, on an external drive that stays unplugged or on a cloud service;
- every so often, open a few files from the backup and see whether they open, instead of believing the "backup complete" message;
- copy first, check, and only then delete the original.

<!-- src: original -->
The fourth habit is the one almost nobody practices, and it's the one that saved me twice in the same month. A tool's green light is the tool talking about itself. The proof is in the destination, compared with the source.

And the cleanup habit is worth keeping too: when the decision is destructive, ask someone else to look at the plan first. The agent that ran my cleanup found two defects that the agent that wrote the plan hadn't seen. People work the same way.

<!-- src: original -->
The concrete step-by-step, tool by tool and system by system, is in @sec-apB. What I'd like you to take from this chapter is simpler.

An AI agent is a fast, eager intern with the root password. You don't need to be afraid of it. You need to set up the house so that its worst mistake costs you an afternoon, at most.

An agent running loose on your system is just the most recent stress test of your discipline. If one wrong command can cause permanent loss, the vulnerability was always there, waiting for a mistake of yours, a bad drive or a piece of ransomware. The agent was just the messenger that arrived first.
