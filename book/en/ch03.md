# A Model With Hands {#sec-ch03}

<!-- src: original -->
So far we've looked at the model by itself: what it is and why it forgets. This chapter is about what happens when it gets hands, a program around it that lets it open files, run commands and check its own work. The discovery I want to show is simple to state and only became clear once I measured: the same model, with nothing changed inside it, can go from failure to the elite depending on that program. It started with an error message.

<!-- src: 2026/05/04/llm-benchmarks-deepseek-unlocked-deepclaude -->
In early May 2026, a Chinese model was giving me a headache. For a month I'd been running a [benchmark]{.gls} of my own, a battery of tests in which every AI model gets the same programming task and then somebody checks what came out. That benchmark gets its own chapter (@sec-ch11). Here only one of its characters matters: DeepSeek V4 Pro.

DeepSeek simply wouldn't let itself be measured. Every time the conversation got past the first round, the answer came back with a curt error: *"reasoning_content must be passed back to the API"*. In plain words, the model's reasoning has to be sent back. From the second request on, nothing worked.

<!-- src: 2026/05/04/llm-benchmarks-deepseek-unlocked-deepclaude -->
The worst part was what I found when I looked closely. The tool I was using to run the model, OpenCode, an open source coding agent, buried the error in its logs and, without telling anyone, handed the work to another model: Anthropic's Claude Opus 4.7.

The runs "completed." The files showed up on disk. Except a good chunk of that code had been written by Opus, with DeepSeek's name on the label.

The score DeepSeek had gotten in that setup, 69 out of 100, measured mixed authorship. In practice, the model was impossible to measure.

<!-- src: 2026/05/04/llm-benchmarks-deepseek-unlocked-deepclaude -->
Then along came DeepClaude, a small script that tricks Claude Code [@aattaran2026deepclaude]. Claude Code is Anthropic's own coding tool, built to talk to the Claude models. The script swaps the address it talks to, and Claude Code starts sending every request to another model without ever noticing the swap.

I pointed Claude Code at DeepSeek V4 Pro. Same model, same task, same request, no other change. The error vanished, both variants I tested ran end to end, and the scores were 84 and 89. The model I couldn't even measure landed straight in the top band of my table, [tier]{.gls} A.

That's 15 to 20 points, gained without touching the model. What changed was the program around it.

## What a Model Can Do on Its Own

<!-- src: 2026/05/25/primeiras-impressoes-usando-oh-my-pi-e-opencode -->
Start with what the model is. An [LLM]{.gls} takes in text and puts out text (the next-word prediction machine from @sec-ch01). It opens no files. It doesn't run programs, doesn't browse the internet, doesn't save anything on your computer.

When you chat with a chatbot on a website, the most it does is write. Ask for code and it writes the code on the screen, and the one who copies, pastes, runs it and comes back to report the error is you. You are its hands.

An [agent]{.gls key=agente} is what happens when somebody takes you out of that role. It's the same model, placed inside a program that reads files, runs commands and hands the results back to it, in a loop, until the task is done. That surrounding program has a name: [harness]{.gls}.

A harness is the gear that straps in and steers a horse. The metaphor works. The raw model is strong, but without a harness it runs off wherever it pleases.

<!-- src: 2026/02/08/rant-ia-acabou-com-programadores -->
Strip away the details and an agent has three parts:

- a **system prompt**, the behavior instructions the program places ahead of everything you type;
- a set of **tools** the model can ask to use;
- a **loop**, which calls the model, executes what it asked for, hands back the result and calls it again.

Each one deserves a close look, because none of them is magic.

### The Instructions Nobody Reads

<!-- src: 2026/02/08/rant-ia-acabou-com-programadores -->
The [system prompt]{.gls key=system-prompt} is a text written by whoever built the tool. It goes in front of every conversation, out of your sight, and tells the model who it is, how to behave and what it may or may not do. The difference between using the model in the website chat and using the same model in a coding agent lies, to a large extent, in that text.

<!-- src: 2026/05/25/primeiras-impressoes-usando-oh-my-pi-e-opencode -->
In May 2026, comparing harnesses, I went to check the system prompt of Oh-My-Pi, an alternative harness loaded with tools. It told the model to do things like:

- use a tool whenever it makes the answer more correct;
- make several calls at once when possible;
- prefer its own reading and search tools over improvising with terminal commands;
- split the work with other agents when the work can be split.

None of this is a trade secret. These are instructions in plain language, the kind you'd give an intern on day one. And they make a difference, because the model needs to know when to use each tool. The big models follow them well when the instruction is clear.

### Asking Is Not Doing

<!-- src: 2026/10/12/llms-agentes-competente-o-suficiente -->
The second part is [tool calling]{.gls key=tool-calling}. The model is still only writing text. The difference is that it learned to write, in an agreed format, a request like "read such-and-such file" or "run this command." The harness recognizes the request, actually carries it out and pastes the result back into the conversation, as if it were a new message.

OpenAI opened this feature to developers in June 2023 [@openai2023function]. Since then, every big vendor trains its models to request tools in this format.

<!-- src: 2026/10/12/llms-agentes-competente-o-suficiente -->
In late 2024, Anthropic proposed a standard for plugging tools into any agent, MCP (Model Context Protocol) [@anthropic2024mcp]. It works like a standard wall socket: whoever writes a tool following MCP can plug it into many different agents without rewriting a thing. The idea caught on, OpenAI signed on months later, and in December 2025 Anthropic donated the standard to a foundation tied to the Linux Foundation [@anthropic2025aaif].

<!-- src: 2026/05/25/primeiras-impressoes-usando-oh-my-pi-e-opencode -->
MCP is text too. Each tool's description goes into the instructions the model reads, and that's how it learns the tool exists.

### The Loop

<!-- src: 2026/05/25/primeiras-impressoes-usando-oh-my-pi-e-opencode -->
The third part is the one that gives you the feeling somebody's at work. Think of the old way, the website chatbot. The model suggests a command, you copy it to your terminal, run it, pick a slice of the output, paste it back and hope you picked the right slice. The model goes blind exactly where it matters: the full error, the order in which things happened, the warning that showed up before the error.

In the agent, the harness does the running. It executes the command, grabs the entire output and hands it back to the model as a new message. It costs more text, but that's how the model gathers enough information to choose its next step.

<!-- src: 2026/10/12/llms-agentes-competente-o-suficiente -->
In a good session, almost none of this reaches you. The model guesses wrong, the agent runs the real test or fetches the documentation, the error comes back, and the model corrects itself. You see the task requested and the task delivered. In between, dozens of little corrections happened that nobody witnessed.

<!-- src: 2026/09/07/desafio-pra-ia-converter-roms-de-nes-pra-master-system-sms -->
The clearest case I lived through in 2026 was a stubborn project: converting Nintendo NES games to run on Sega's Master System. While the models translated the code blind, the project stalled. It only got moving again when the agent started running the original game and the translation in emulators (programs that imitate the console on a computer), side by side, measuring the difference and correcting based on what it had measured. That story gets its own chapter (@sec-ch08).

![An agent's loop: the model thinks, asks for a tool, the harness runs it and returns the result, and the model decides again.](assets/figures/en/ch03-laco-do-agente.png){#fig-ch03-laco-do-agente fig-alt="A circular diagram with four stages connected by arrows: the model thinks, asks for a tool, the harness executes (compile, run test, read file), the result comes back to the model as text. In the center, the word 'task'. An exit arrow leads from 'the model thinks' to 'done', when the result matches the request. A legend separates the model's stages, where it only writes text, from the harness's stages, where the hands are."}

<!-- src: 2026/10/12/llms-agentes-competente-o-suficiente -->
No piece of this cycle is intelligent on its own. The test only points out the error. The harness only passes text along. The model only writes.

But the model getting it wrong, the test flagging it and the model fixing it, dozens of times, with nobody in between, add up to something that from the outside looks like a programmer at work.

> The model only writes text. The harness is the one with hands.

## A Harness Cut to Fit

<!-- src: original -->
If it's all text, any harness would do for any model. In practice, not quite.

<!-- src: 2026/02/08/rant-ia-acabou-com-programadores -->
Coding models were trained to ask for tools, and the tools change from vendor to vendor. Codex has the model search code with rg, a search program; OpenCode uses grep, another program that does the same thing.

<!-- src: 2026/05/25/primeiras-impressoes-usando-oh-my-pi-e-opencode -->
And the differences go beyond the list of tools. Each harness decides what information the model sees, in what format it describes a file change, when the conversation gets summarized, when another agent is called and when the work stops.

<!-- src: 2026/04/15/como-falar-com-o-claude-code-efetivamente -->
In April 2026, I was switching between Claude Code and Codex in my everyday work. As models, Claude Opus and GPT-5.4 looked tied to me: when one couldn't pull off a hard task, I swapped to the other, and the other usually did. What made me prefer Claude Code was the harness.

Claude Code broke a long task into a to-do list visible on screen and didn't drop items, so when it said "done," I could check. And when I interrupted to ask for something else, it usually kept the first task running and started the second alongside it. Codex, in the same situation, stopped the first one and didn't always manage to pick it back up where it had left off.

### When the Maker's Harness Gets in the Way

<!-- src: 2026/05/25/primeiras-impressoes-usando-oh-my-pi-e-opencode -->
By May the story had gotten more tangled. After hundreds of hours of use, I considered Claude Code one of the best harnesses around. You can plan before executing, interrupt midway and change direction without wrecking the session, and it manages the conversation's memory better than the competition.

Codex, on the other hand, was a weak harness around an excellent model. Its planning mode was poor, interruption was clumsy, and more than once it dropped the job halfway until I told it to finish properly. Running the same GPT-5.5 inside OpenCode, the model felt much less held back.

<!-- src: ref:llm-coding-benchmark/README.md -->
And OpenCode has invisible hands of its own. It looks at the model's name and injects a different system prompt for each family: one text tailor-made for the Claude models, another for GPT, another for Gemini, another for Kimi. Everybody else, DeepSeek included, gets a generic text. Two models "running in the same OpenCode" didn't always read the same instructions.

<!-- src: 2026/05/25/primeiras-impressoes-usando-oh-my-pi-e-opencode -->
So not even the most intuitive rule, using each model in its maker's tool, holds up. What's left is a more boring and more useful rule. You never use a model. You use a combination of model and harness, and the combination is what needs testing.

## The Bill That Arrives Before You Type

<!-- src: 2026/09/17/falando-um-pouco-sobre-minhas-skills-de-ia -->
All of this has a cost, and the cost is measured in [tokens]{.gls key=token}, the little chunks of text the model reads and writes (@sec-ch01). Take [skills]{.gls key=skill}, packages of instructions you install in the agent to teach it specific tasks (how to write your own is the subject of @sec-ch09) [@anthropic2025skills]. To use a skill, the model needs to know it exists, so the harness pastes the name and description of each one into the opening instructions. The full text only goes in when the agent decides to use the skill.

<!-- src: 2026/05/25/primeiras-impressoes-usando-oh-my-pi-e-opencode -->
Add the system prompt and each tool's description. Every session starts with a pile of text you didn't write: you open the tool, type nothing, and you've already spent. Some people switch harnesses just to slim down that pile.

Those savings are pocket change. In a real coding agent, the bulk of the spending comes from the work: reading code, running tests, receiving the full error message, reading the log of a program that spits out a warning on every line. A single chatty test log already fills the [context window]{.gls key=janela-de-contexto} of a small model, that limit on how much text it can keep in front of it at once (@sec-ch02).

That's why my personal rule is to never use a serious coding agent with less than 200,000 tokens of context. Below that, the harness has to summarize the conversation all the time, and every summary loses the detail that was the clue.

### Rereading Without Paying Twice

<!-- src: 2026/10/12/llms-agentes-competente-o-suficiente -->
There's a technical detail that changes the whole bill. The model keeps nothing between one request and the next. On every turn of the loop, the harness resends the whole conversation from the top: the instructions, the tool descriptions, every file read, every error received. In a long session, that becomes a mountain of text reread hundreds of times.

[Prompt caching]{.gls key=prompt-caching} takes care of a good part of that. The server stores the processing of the opening stretch of the conversation, which hasn't changed, and charges much less when it comes around again. When Anthropic launched the feature, in August 2024, it announced up to 90% off the cost of long, repeated text [@anthropic2024caching].

<!-- src: ref:llm-coding-benchmark/docs/success_report.multi_model.md -->
The size of the effect shows in my numbers. In a single benchmark run, in April 2026, Claude Code reread 6 to 11 million tokens from the cache: its own instructions, the tool descriptions and the history, resent on every turn. Without caching, sessions like that would cost a lot more.

<!-- src: 2026/05/04/llm-benchmarks-deepseek-unlocked-deepclaude -->
DeepClaude, as it happens, had a weak spot right here. The markers Claude Code adds to request caching got dropped on the floor on the way to DeepSeek, which has an automatic cache of its own, but without the explicit markers. Result: each turn came out a little more expensive than it would have on a direct call to Anthropic. It also didn't accept images or MCP tools.

### The Thinking That Has to Come Back

<!-- src: 2026/10/12/llms-agentes-competente-o-suficiente -->
Now the error from the start of the chapter makes sense. In September 2024, OpenAI launched o1, a model trained to write out a long chain of [reasoning]{.gls key=raciocinio} before giving its final answer [@openai2024o1]. By my reading, that was the last big leap in the models' reasoning. Since then, almost every big model has a mode like that: it "thinks" in writing, spends more tokens and makes fewer mistakes.

<!-- src: 2026/05/04/llm-benchmarks-deepseek-unlocked-deepclaude -->
DeepSeek returns that thinking in a field separate from the answer, the *reasoning_content* from the error.

Its documentation is clear: when the conversation uses tools, that field has to be sent back in full on every following request, or the API, the door other programs use to talk to the service, rejects the request [@deepseek2026thinking]. The library OpenCode used under the hood threw the field away when it built the next request. Turn one, fine. Turn two, rejected.

A fix for OpenCode had landed in late April, but it required manual configuration, and when I ran the tests either it hadn't arrived yet or I didn't have the configuration in place. DeepClaude didn't even need it: the path it used handled the thinking properly from the start.

> When you evaluate a model, you're evaluating a model inside a harness. Nobody uses the model alone.

## The Invisible Half of the Result

<!-- src: 2026/05/04/llm-benchmarks-deepseek-unlocked-deepclaude -->
The DeepSeek story has two lessons, and the first one isn't even about AI. A tool can hide an error and deliver a result that looks correct. The files were there, the run said "completed," and underneath, another model had done the work. If I hadn't gone looking, I'd have published a score for DeepSeek that belonged to Opus.

That goes for anyone using any AI tool: the screen saying "done" and the work being right are two different things, and only one of them is visible without opening the box.

The second lesson is that the same model went from "impossible to measure" to the top just by swapping the program around it.

### The Same Opus, Two Results

<!-- src: ref:llm-coding-benchmark/docs/success_report.multi_model.md -->
DeepSeek wasn't the only case that seemed to point at the harness. In April 2026, the benchmark report had logged something strange with Claude Opus 4.7. Inside OpenCode, it used the library the task called for the right way. Inside Claude Code, the tool made by its own maker, two out of three runs used the library in a way the audit at the time classified as wrong.

The hypothesis was that Claude Code's instructions and tool descriptions were nudging Opus toward a generic pattern, learned from another, similar library.

<!-- src: 2026/04/24/llm-benchmarks-parte-3-deepseek-kimi-mimo -->
At the time, I concluded the problem was the combination: that harness was getting in that model's way. Days later, checking the library's source code, I found out that usage was correct (@sec-ch11). With that, the Opus case left the list of evidence for the harness effect and joined the list of evidence that my own audit needed auditing.

<!-- src: ref:llm-coding-benchmark/docs/success_report.multi_model.md -->
In July, Claude Opus 5, running alone inside that same Claude Code, did the best engineering work the benchmark had seen up to then. And a more careful re-audit lowered the score of the "champion" Opus 4.7 in OpenCode. Measurements get things wrong too, and how they do is the subject of @sec-ch11.

### The Plugin I Forgot I Had On

<!-- src: ref:llm-coding-benchmark/docs/success_report.v2.md -->
The cleanest measurement came by accident, in late July. Day to day, I use a plugin for OpenCode that turns the agent into an orchestrator: a main model that splits the work and hands pieces out to other agents. I discovered that plugin was leaking from my personal configuration into the benchmark runs. Eleven models had been measured with it switched on, without my knowing.

I redid the eleven runs with a clean OpenCode, no plugins at all. Same model, same task, only the harness different.

<!-- src: ref:llm-coding-benchmark/docs/success_report.v2.md -->
MiniMax M3 went from 24 to 91 points. With the plugin, it took the orchestrator role as an order to delegate and wait, and delivered next to nothing. Grok 4.3 went the opposite way: from 57 it fell to 18, because it leaned on the plugin's structure as a crutch and, without it, gave up in under a minute, twice in a row.

Plus 67 points for one, minus 39 for the other. The plugin, and nothing else, pushed two models in opposite directions.

<!-- src: ref:llm-coding-benchmark/docs/success_report.v2.md -->
The strongest models barely moved. Grok 4.5 and GLM 5.2 shifted by one point, within the noise. The report noted that nothing else across both versions of the benchmark, not model generation, not price range, not vendor, produced an effect that size.

> The harness is half the result. Sometimes, more than half.

### Three Reviewers, Three Answers

<!-- src: 2026/05/25/primeiras-impressoes-usando-oh-my-pi-e-opencode -->
You don't need a benchmark to see this. In May, I asked three combinations to review the same code change: Oh-My-Pi with GPT-5.5; OpenCode with the same GPT-5.5; and Claude Code with Claude Opus 4.7. Same code, same request, same intention: find the problems before approving.

None of them found everything. To simplify, if the problems were A, B, C and D, one found A and B, another found B and C, the third found C and D. And the same GPT-5.5, in two different harnesses, gave different answers. The harness changes the instructions, the tools, the order in which things show up, and that changes the path the model takes.

<!-- src: 2026/05/25/primeiras-impressoes-usando-oh-my-pi-e-opencode -->
The reverse of the sales pitch holds too. More agents working at the same time don't make programming faster. Programming has a critical path, just like managing a team: one decision depends on the previous one, which depends on a test that hasn't run yet.

When I let the strong models choose, in the benchmark, they simply didn't delegate. When I forced them to, quality dropped or time went up. Parallel agents handle independent batches, like converting two hundred images, and independent batches are the easy part.

## Why It Felt Like a Leap

<!-- src: 2026/10/12/llms-agentes-competente-o-suficiente -->
If you used these tools between 2025 and 2026, you know the feeling. Suddenly the AI started doing things it couldn't do a year earlier. Tasks that used to come back to you in pieces, one error at a time, started coming back finished. The temptation is to conclude that the models got a lot smarter.

Look at the dates, though:

- tool calling has been around since 2023;
- written-out reasoning, since 2024;
- MCP and prompt caching, also from 2024;
- Claude Code and Codex came out in 2025.

No piece was new in 2026. What changed in that stretch was how well it all got tied together.

<!-- src: 2026/10/12/llms-agentes-competente-o-suficiente -->
There's a mechanism behind it. A lone model has to get it right on the first try, with whatever it has stored in its [weights]{.gls key=pesos} since training. A model with a harness can fetch the documentation the moment it needs it, test a hypothesis, read the error and try again. Each turn of the loop brings new information into the session without costing a lick of training.

That attacks the invention of facts, the subject of the next chapter, at its root. Search brings in the fact the model doesn't know by heart, and the test catches the invention before it becomes code. As long as there's a test, or something else that measures reality (@sec-ch08). Without that, the loop spins in a vacuum.

<!-- src: 2026/10/12/llms-agentes-competente-o-suficiente -->
People who measure this from the outside see the same shape. METR, an independent organization that evaluates models, measured the length of the tasks agents can complete with 50% success and saw that length double roughly every seven months since 2019 [@metr2025tasks]. What that metric measures is a system's ability to work on its own, with tools, for longer.

### The GPT-4 Test

<!-- src: ref:llm-coding-benchmark/docs/success_report.v4.combined.md -->
In late September 2026 I ran a check that convinced me. I put two models from the previous generation, GPT-4o and GPT-4.1, into the benchmark, in the same harness the current models ran in. Neither one completed the task without me holding its hand.

GPT-4o wrote down the plan of what it was going to do and stopped right there, without calling a single tool. GPT-4.1 kept researching and summarizing instead of building. When they did engage, they could even program. Meanwhile, practically every model from 2025 and 2026 ran the task's seven stages on its own, start to finish.

<!-- src: original -->
What separated the generations, in this test, was the ability to use tools in sequence, unsupervised, stage after stage. And that ability is something the vendors started training for on purpose, along with their harnesses. So the line between brain and hands is blurrier than the image suggests: part of the hands lives inside the model, learned in training. What I'm claiming is narrower: base reasoning changed little, and the ability to act is what grew.

That left me with a suspicion that took me until October to check. If the leap everyone felt came more from the hands than from the brain, what about the promises of intelligence growing without end? I come back to that question in the last chapter (@sec-ch20), with what was measured outside over the year and with my own numbers.

### What's Missing When There Are No Hands

<!-- src: original -->
There's a side to this story that matters to people who will never open a coding agent. Everything that worked in this chapter depended on something outside checking the model: the test failing, the emulator showing the difference, the documentation saying otherwise. The harness gives the model hands to trip over reality and correct itself.

Now take the harness away. No compiler, no test, no search. What's left is the bare model, the way you probably use it: a chat box, you on one side, asking about health, money or the news of the day.

<!-- src: original -->
Nothing there checks anything. And the model does what it was trained to do: produce the most likely text, which is often the text you wanted to read.

<!-- src: 2026/03/27/ensinando-a-questionar-noticias-frank-investigator -->
In March 2026, I started building a tool to question the news. It puts three different models to work checking the claims in each story. To understand why I distrusted a single model so much, you need to understand why it tends to agree with you.
